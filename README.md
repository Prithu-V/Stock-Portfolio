# Stock Portfolio & Investment Tracker

A relational SQL project that models a real-world stock portfolio and investment tracking platform. The project demonstrates production-oriented SQL techniques for **finance and investment analytics**, including schema design, data generation, business logic, aggregations, CTEs, and window functions.

## Project Overview

Investment platforms generate data across investors, portfolios, stocks, trades, market prices, and dividends. This project builds a normalized relational database to manage these entities and answer practical financial analytics questions.

The project focuses on:

* Tracking capital deployed across portfolios
* Calculating realized profit and loss
* Calculating dividend income using ex-date logic
* Identifying highly traded stocks
* Ranking stocks within sectors
* Analyzing price trends using moving averages
* Segmenting investors based on investment levels
* Tracking cumulative capital deployment

## Database Schema

The database contains six tables:

| Table          | Type      | Purpose                                         |
| -------------- | --------- | ----------------------------------------------- |
| `investors`    | Dimension | Stores investor information                     |
| `portfolios`   | Dimension | Stores investment accounts owned by investors   |
| `stocks`       | Dimension | Stores tradeable equities                       |
| `trades`       | Fact      | Records BUY and SELL transactions               |
| `daily_prices` | Fact      | Stores historical OHLCV market data             |
| `dividends`    | Fact      | Stores dividend payouts and ex-date information |

The database follows a **star-schema-style structure**, where `trades` and `daily_prices` act as high-volume fact tables while `investors`, `portfolios`, and `stocks` provide descriptive context.

### Key Relationships

```text
investors
    │
    │ 1:N
    ▼
portfolios
    │
    │ 1:N
    ▼
trades ◄──────── stocks
  │                 │
  │                 ├──── daily_prices
  │                 │
  │                 └──── dividends
  │
  └── BUY / SELL transactions
```

## SQL Analysis

The 12 analytical queries are organized into three tiers of increasing complexity.

### Tier 1 — JOINs & Aggregations

Fundamental queries used to establish the analytical layer.

**Q1. Total Capital Invested per Portfolio**

Calculates portfolio-level capital deployment, including trading fees.

**Q2. Trade Count per Investor**

Separates BUY and SELL transactions using conditional aggregation.

**Q3. Most Traded Stocks**

Identifies the top stocks by total shares traded.

**Q4. Current Net Shares Held**

Calculates current holdings by treating BUY quantities as positive and SELL quantities as negative.

**Q5. Total Fees Paid per Investor**

Measures fee revenue generated by each investor.

### Tier 2 — Subqueries & CTEs

These queries solve multi-step analytical problems using intermediate calculations.

**Q6. Portfolios Above Platform Average**

Identifies portfolios whose investment exceeds the platform-wide average.

**Q7. Realized P&L on SELL Trades**

Calculates realized profit or loss using a weighted average buy-price cost basis.

```text
Net P&L =
(Sell Price - Average Buy Price) × Quantity - Fees
```

**Q8. Dividend Income per Investor**

Calculates dividend income while applying the ex-date rule and determining the number of shares held before each dividend date.

### Tier 3 — Window Functions

Advanced analytical queries that calculate rankings, running totals, moving averages, and customer segments without collapsing individual rows.

**Q9. Stock Ranking Within Sector**

Uses `RANK()` and `PARTITION BY` to create sector-level stock rankings.

**Q10. Running Total Invested**

Uses a cumulative `SUM() OVER()` to track capital deployment over time.

**Q11. 7-Day Moving Average**

Uses a windowed `AVG()` to smooth daily closing-price data and identify price trends.

**Q12. Investor Quartile Tiering**

Uses `NTILE(4)` to divide investors into four investment-level groups:

| Quartile | Tier     |
| -------: | -------- |
|        1 | Standard |
|        2 | Silver   |
|        3 | Gold     |
|        4 | Platinum |

## Important Business Logic

### Weighted Average Cost Basis

The project uses:

```text
Weighted Average Buy Price =
SUM(Quantity × Price) / SUM(Quantity)
```

This is used instead of simply averaging purchase prices because purchases can occur at different quantities and prices.

### Dividend Ex-Date Logic

An investor is considered eligible for a dividend only when shares were held before the dividend's `ex_date`.

The analysis therefore applies:

```sql
trade_date < ex_date
```

and then calculates net holdings using BUY minus SELL quantities.

### WHERE vs HAVING

The project demonstrates the distinction between:

* `WHERE` → filters rows before aggregation
* `HAVING` → filters aggregated results after `GROUP BY`

This is particularly important when filtering based on `SUM()`, `COUNT()`, or `AVG()`.

### GROUP BY vs Window Functions

`GROUP BY` reduces multiple rows into groups, while window functions perform calculations across related rows while preserving individual records.

This makes window functions suitable for:

* Running totals
* Rankings
* Moving averages
* Time-series analysis

## Database Design Decisions

Several design choices were made to improve data integrity and query performance:

* `ENUM` restricts `trade_type` to `BUY` or `SELL`
* `DATE` is used where time-of-day information is unnecessary
* A unique constraint on `(stock_id, price_date)` prevents duplicate daily prices
* Indexes are applied to high-traffic columns such as `trade_date`, `portfolio_id`, and `price_date`
* Foreign keys are stored in child tables to maintain relationships between entities
